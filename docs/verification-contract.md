# Verification contract / 投資系統交付驗收契約

本規則和功能程式分開審查；不得為了讓失敗測試變綠而降低斷言、刪除測試或更改驗收標準。

## 完成狀態

- **Implemented**：程式已寫入分支，尚未驗證。
- **Tested offline**：有對應 commit SHA 的實際測試結果；列出失敗與跳過項目。
- **Staging verified**：隔離環境的端到端與資料庫權限驗證，有實際輸入、輸出及回復證據。
- **Production verified**：取得正式授權、真實 LINE 訊息與舊版相容性驗收、回復演練完成。離線測試不能替代。

## 高價值驗證矩陣

| 類型 | 驗收項目 | 現狀 |
| --- | --- | --- |
| 端到端 | LINE 股票代碼、清單、資料狀態、一般文字、follow、unsend、群組及每日報告 | 隔離整合測試存在；真實 LINE 尚未驗收 |
| 鐵則 | HMAC 無效不寫入；停用入口 HTTP 503；股票資料庫只讀；Reply 交付狀態去重；禁止虛構行情 | 既有單元/整合測試與資料庫品質稽核 |
| 差異 | 同一非股票事件直接呼叫舊版與經閘道代理的可觀察行為一致 | 模擬路由已測；真實舊版黑箱差異測試待補 |
| 資料完整性 | OHLC 合法、評分 0–100、覆蓋率 0–1、不可把單日行情當作足夠歷史 | 現有唯讀 DB audit 工作流程 |
| 回復 | 舊版 Deployment 4 不覆蓋；能恢復 LINE Webhook 舊 URL | 既有復原流程；正式切換尚未執行 |

## 修改觸發的可靠度清單

1. `src/**`：Python 測試；涉及行情或評分時執行正式只讀資料品質稽核。
2. `line-stock-analysis/**`：Node 測試、原版/候選 bundle，以及候選預設停用 HTTP 503 smoke；涉及分流則需新舊差異驗證。
3. 憑證、LINE Webhook、權限或 production DB：須由維運者授權受控 canary 與端到端測試，不能由一般 CI 自動切換。
4. 每次驗收都需留下 commit SHA、測試分類、執行結果與未驗證範圍；不得在測試證據中儲存 LINE Token、私人訊息或連線密碼。

## 三輪修復及升級人工處理

同一失敗最多進行三輪根因修復；每輪記錄失敗項目、修正內容與新證據。第三輪仍不通過，或涉及真實使用者與正式變更時，停止自動變更並請負責人裁決。驗收契約的修改需單獨審查，不能與被驗功能一起悄悄調整。

## 觀察模式

`.github/workflows/verification-evidence-observe.yml` 對 PR 的 Python/LINE 測試產生分項 JSON 證據，先不作強制合併門檻。失敗結果應被記錄及修復，但不能聲稱工作流程全綠即代表正式環境通過。觀察誤報率、耗時及真正攔截缺陷後，再決定將穩定規則提升為強制檢查。

**正式 LINE 上線紅線**：在新閘道受保護環境配置相同頻道的 Secret/Token、官方已簽章空事件測試、真實訊息及舊版相容測試、收件者不變、可回復及明確切換授權完成以前，保持 `linewebhook` Deployment 4 和正式 Webhook URL 不變。
